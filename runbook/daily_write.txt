# 日次レポートの書き方 daily_write v1.1（daily_runbook v2.8 と対）
# 書き手（定期実行の Agent。チャットで「日次レポート」を頼まれたときは Claude 自身）が読む。定期実行の流れは daily_runbook.txt、変更の履歴は runbook/CHANGELOG.txt。

## 役割
米国株指標チェックの日次レポート（マスター仕様 v4.2 の D7「Daily」）を書く。
前営業日の米国終値を基準に、相場全体の値動き（Tape）を中心とした短い更新と、今夜の Daily Plan をまとめる。

## 進め方（この順に）
1. このファイルを最後まで読む。
2. 入力を読む（下の「入力」）。
   この段階では Web 検索をしない（値動きの理由やニュースを探し始めない）。Web 検索が使える場面と回数は、下の「Web検索」で決まっている。
3. 書く：「ひな形」の表の節を書く。
   書き始める前に、「ひな形」の表の行（10行）をやることリストに入れる（TaskCreate が使えるとき。無ければ /home/claude/todo_us_daily.md に書く）。1つの節を書き終えるごとに消す。
   1節（重要ポイント）から「読み方」まで順に、1つの節ごとに次の3つを繰り返す：
   (a) その節のファイル（runbook/daily/ にある。ひな形の表に名前がある）を読む。
   (b) その節を書く。
   (c) その節のファイルを上から1行ずつ見て、書いた内容と突き合わせる（1行が1つの決まり。その日は当てはまらない行は飛ばす）。足りないものがあれば、その場で足す。
   節のファイルを先にまとめて読まない（書く直前に読むほうが、その節の決まりを落とさないため）。
   冒頭（題と作成の行・今日のひとこと・なぜその判断か）は、ほかの節を書き終えてから最後に書き、レポートの先頭に置く（全部の節の中身がそろってからまとめるため）。
   途中で止まらない：全部の節と「書き終えたら」が済むまで、文だけの返答で終えない（返答を終えると、そこで作業が止まる）。
4. 書き終えたら、下の「書き終えたら」を行う。

## 入力

- /home/claude/market-data/02_User_Settings.txt（ユーザー設定。null の項目は未設定として扱う）。
- /home/claude/state/state/latest_daily.json と /home/claude/state/state/scenarios.json（前回の状態。流れの側が保管ページの state/latest_daily・state/scenarios を保存したもの）。無ければ「前回比較不能」と書く。
- 言葉づかい：/home/claude/market-data/05_Plain_Language_Glossary.txt（下の「書き方」）。
- 定義の確認が必要なときだけ、マスター仕様と追補の該当条項を読む（/home/claude/market-data/ にある）：
  C7.1、C15.1、C15.2、D4、D7、E9〜E14、F2.1、F4、F9、
  追補03のE7.1〜E7.3、追補04のC15.1a〜d、追補06のE7.4・C10.1・F10、追補07のE6.2・E6.3・E9.2a・E9.5a・E9.6・E9.7・E10.1a・E13.2、追補08のB4.5a・B4.6a、追補09のF11。C15.1と04が食い違えば04を優先。本文と07が食い違えば07を優先。

## 原則
- 計算はGitHubの解析エンジン（analyze.py）が済ませている。
  signals.json の値を再計算しない。
  検証のための再計算は可。
  食い違いがあれば signals.json を優先し、食い違いを報告する。
- 推測で埋めない。
  null や missing はそのまま「未確認」と書く。
- 口座・保有・売買ログはユーザーがチャットで示した範囲だけ使う。
  未提供なら数量を出さない。
- 冒頭ブロック → 重要ポイントの順に先頭に置く。
- GitHubのリポジトリのファイルは変更しない。
  例外は、データが古いときのワークフロー起動（daily_runbook.txt 第2節）、レポート本文の reports/ への保存（同 第9節）、週の最初の日次での reports/flows/fuel_latest.yaml の更新（Broad の節）だけ。

## 分量の決まり
- 本文の目安は表を含めて約7,000字（重要な変化が多い日は超えてよい）。
  最初の1画面（冒頭ブロックと重要ポイント）で判断でき、残りは必要なときに読む形にする。
- 変化を先に、変わっていないものは短く。
  その節に関わる key_events が無い日は、短縮形で書く。
  短縮形の形は、それぞれの節のファイルにある（半導体・テクノロジーのステージ分析／相対強度・調整耐性・RSライン／tech_watch など、Daily Plan、データ状態）。
- 短縮しないもの：冒頭ブロック、重要ポイント、Tape の表と中身のまとめ、Broad、半導体・テクノロジーの「テック内部」1行と ETF の表とセットアップ。
- 同じ数字を2つの節に書かない（冒頭ブロックに書いた数字は、該当の節で内訳を足すときだけ再掲する）。

## Web検索（使える場面と回数の上限）
- Web検索は、当日〜翌営業日のイベント（経済指標・決算・FOMC）と、指数が大きく動いた日の理由の確認だけに使う（合計2回まで。WebFetch は検索結果に出たURLしか取れない）。
  指数・金利・為替・原油の数字を記事から取らない。
  原油の水準（WTI の価格）が要る日だけ、理由の記事にある値を reported_unverified と明記して1つ書いてよい。
- 別枠：その週の最初の日次だけ、買い戻しの燃料の控えの更新に検索1回＋取得1回（runbook/daily/s3_broad.txt の最後の項目）。
- 使った回数を数えておき、最後に返す。上限に達したら、残りは「未確認」と書いて先へ進む。

## 数字の出所と基準
- 個別銘柄・ETF・指数の騰落率と出来高は、signals.json（market・tech_etf・sector_etf・movers）と screen.csv（chg_1d_pct・chg_1w_pct・rvol50）の値だけを書く。
  記事に載っている騰落率は取引時間中の値のことがあるので書かない（11/9 の日次は記事の「NVDA −4.6%、AMD +9.2%」を載せたが、データは −4.27%、+13.26% だった）。
  記事は値動きの理由の説明にだけ使う。
  signals.json に movers が無い日（エンジンを更新する前に作られたデータ）は、prices_daily.csv.gz の終値から前日比を計算して書く（その旨をデータ状態に1行）。
- 高値からの位置は、tape.checklist・market・tech_etf・screen の pct_from_52w_high（取引時間中の高値が基準）にそろえる。
  同じ銘柄に2通りの数字を書かない（rs_lines.spy_pct_from_52w_high は終値が基準で少し違う値になるので、本文には書かない）。
- 倍率には基準を書く：rvol50 は「出来高が50日平均の○倍」。
  「普段の○倍」とだけ書かない（半導体の日次は20日平均が基準で、同じ銘柄でも別の数字になる）。

## 書き方（言葉づかい）
- 状態を表す語は 05_Plain_Language_Glossary.txt（https://raw.githubusercontent.com/bakaho19920625-wq/market-data/main/05_Plain_Language_Glossary.txt。
  届かなければ保管ページの spec/plain_language.txt）の「言葉」で書き、数字と記号を括弧で後ろに付ける（例：大口が売った日が7日（IX2＝7、6日以上は危険水準））。
  記号は消さない。
  記号だけ・英語だけの行を作らない。
  表には「言葉」の列を置くか、数字の横に言葉を添える。
  巻末に「読み方」（使った記号だけ、1行ずつ）。
  冒頭ブロック（今日のひとこと・なぜその判断か）では、記号・英語の略語を単独で使わない（×「Tape C確定」「崩れガード成立」「FTDなし」「分配日7」→
  ○「高値圏で売りが増えている段階（C、2日続いたので確定）」「指数が50日線を割って大口の売りが5日以上続く安全装置が立っている（崩れガード IX3）」
  「反発が本物になった合図（FTD）はまだない」「大口が売った日が直近5週で7日（IX2＝7、危険水準）」）。
  初出の記号には必ず言葉を添える。

## ひな形（この順番・この見出しで書く）
見出しは省かない・順番を変えない。見出しの後ろに括弧で補足を付けるのはよい（例「## 2. Tape（相場全体の値動き）」）。
その日に書くことが無い節も見出しを残し、節のファイルにある形（「本日の重要イベントなし」など）で書く。

| 順 | 見出し | 節のファイル（runbook/daily/） | 短縮形 |
|---|---|---|---|
| 1 | `# 米国株指標チェック 日次レポート YYYYMMDD-DAILY` と、基準日・作成・データ生成の行、次の米国取引の行 | a_opening.txt | − |
| 2 | `## 今日のひとこと` | a_opening.txt | − |
| 3 | `## なぜその判断か` | a_opening.txt | − |
| 4 | `## 1. 重要ポイント` | s1_key_events.txt | − |
| 5 | `## 2. Tape` | s2_tape.txt | − |
| 6 | `## 3. Broad` | s3_broad.txt | − |
| 7 | `## 4. 半導体・テクノロジー` | s4_tech.txt | あり（中の項目ごと） |
| 8 | `## 5. Daily Plan` | s5_daily_plan.txt | あり |
| 9 | `## 6. データ状態` | s6_data_status.txt | あり |

## 書き終えたら
1. 見出しが「ひな形」の順にそろっているか見る。
2. 点検プログラムを実行し、「不合格」の行を直す（直したらもう一度実行する）：
   `python3 /home/claude/market-data/tools/check_report.py us_daily <レポートのパス> --data /home/claude/mkt`
   「注意」の行は不合格ではない。読んで、直す必要があるものだけ直す。
3. 保管ページに保存するための控えを /home/claude/out/<report_id>.save.json に書く（流れの側が tools/state_docs.py で文書にする）。形：
   {"meta": {"id": "<report_id>", "report_id": "<report_id>", "mode": "daily", "as_of_market_et": "YYYY-MM-DD", "created_jst": "YYYY-MM-DD HH:MM JST", "title": "米国株 日次レポート YYYY-MM-DD",
    "headline": "一文結論", "broad_score": 数値か null, "broad_regime": "…（据置）", "tape_regime": "A〜F", "alignment": null, "long_level": "…", "hedge_level": null, "gates": ["…"], "data_status": "…",
    "github_path": "reports/daily/<report_id>.md"}, "state_yaml": "UNIFIED_MARKET_STATE: …"}
   state_yaml には Tape、L/H、候補、key_events、データ状態を入れる（マスター仕様 D部の状態の形。前回の state/latest_daily の yaml と同じ項目）。
4. git の操作・保管ページへの保存・配信はしない（定期実行では流れの側が行う）。
   チャットで単独に頼まれたときは daily_runbook.txt の第9節・第8節に従う。
5. 最後に返す：レポートのパス、点検の結果（合格／残った項目）、Web検索の回数、reports/flows/fuel_latest.yaml を更新したかどうか。
