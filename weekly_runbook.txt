## 2. データの新しさと、リポジトリの活動
- signals.as_of_market_date が直近の米国取引日（通常は金曜。NYSE休場日を除く）より古ければ、データ更新を自分で起動する：
  - 起動は git の push で行う（日次と同じ）。
    /home/claude/market-data（第1節）で
    `date -u +%Y-%m-%dT%H:%M:%SZ > refresh/request.txt && git add refresh/request.txt && git -c user.name=claude -c user.email=noreply@anthropic.com commit -m "refresh request" && git push origin main`。
    この push で .github/workflows/update.yml が動く（refresh/README.md）。
    push が断られたら第7節の「push が断られたとき」に従い、それでも駄目なときだけ
    `gh workflow run update.yml --ref main -R bakaho19920625-wq/market-data` を1回試す（エラーなら起動できなかったものとして先へ進む）。
  - 完了は git で確かめる：30秒おきに `git -C /home/claude/market-data fetch -q origin data && git -C /home/claude/market-data show FETCH_HEAD:manifest.json` の prices.as_of を見て、
    直近の取引日になるまで最大12分待ってから取り直す（raw.githubusercontent.com は数分古い値を返すことがあるので待ち合わせには使わない）。
  - それでも古ければ、基準日を明記してレポートを作り、冒頭で「GitHubのデータが最新ではありません」と警告する。
- リポジトリの活動：manifest.repo_last_commit_main から45日以上経過していれば、冒頭で「GitHubのリポジトリを更新してください
  （tickers.txt に1行コメントを足して保存）」と警告する。
  manifest.keepalive が failed でも同様。
  この節の警告（データが古いまま進む／リポジトリの更新／keepalive）に当たったら、第4節で書き手に伝える（レポートの冒頭に書かせる）。

## 5. 点検
- 自分でも点検プログラムを実行する（書き手の報告だけで済ませない。数秒で終わる）：
  `python3 /home/claude/market-data/tools/check_report.py us_weekly /home/claude/market-data/reports/weekly/YYYYMMDD-WEEKLY.md --data /home/claude/mkt`

  SendMessage が使えないとき、または書き手が応えないときは、不合格の節だけ自分で直す（その節のファイルを読んでから）。

- 点検プログラムそのものが動かない・途中で止まるときは、点検を飛ばして先へ進み、配信の同じ場所に「点検プログラムが動かなかった」と1行で書く。
- 「注意」の行は不合格ではない。読んで、直す必要があるものだけ直させる。

## 6. 配信
- SendUserMessage の冒頭サマリは**1画面**（日本語でおよそ800〜1,200字）。
  全文は添付の本文で読めるので、配信には判断に要るものだけを書く：
  1. 冒頭ブロック（レポートの冒頭と同じ文：今日のひとこと3〜4行＋なぜその判断か。ヘッジと長く持つ分の目安はここに入っている）
  2. 前回から変わった点：Tape・Broad の変化（定義変更があればその旨）、持っている分の上限とヘッジの上限（L/H）が変わったか、先導セクターの入れ替わり、半導体・テクノロジーの先導株数（4週前比）。
     モードが Full ならその理由を1行
  3. 1行ずつ：買い戻しの燃料計（棒の行と読み方。追補08）／強気の材料・弱気の材料を各2点まで
  4. 来週のイベント（日付つきで3〜5件）と、データ状態で伝えるべきこと（未更新・missing の多い分野・補完。なければ書かない）
  土台と値動きの一致（Alignment）の説明、27項目の中身、ステージの表は配信に書かない（本文にある）。
  最後に「全文は添付のファイルと、保管ページ（これまでの週次が並ぶ）：https://claude.ai/artifact/MYKcd2wVF1m2Ym26ExEzca」と1行（このリンクは毎回出す）。
  すべて05の言葉で、記号は括弧。
- 本文全体を「YYYYMMDD-WEEKLY.md」として書き、SendUserFile で送る。
  1回に収まらなければ分割し、途中までのものを完成版と表示しない。
- 配信の冒頭サマリは、専門用語を知らない人が読んでも分かる文にする。
- 送る前に、配信の文を /home/claude/delivery.txt に書き、`python3 /home/claude/market-data/tools/check_report.py delivery /home/claude/delivery.txt --max 1200 --link https://claude.ai/artifact/MYKcd2wVF1m2Ym26ExEzca` で長さと最後の行を確かめる。

## 7. 保存
- report_id：YYYYMMDD-WEEKLY（基準日）。
- GitHubへの保存（全履歴の置き場。F9）：第1節で用意した /home/claude/market-data で `git pull -q --ff-only`。
  書き手が書いた本文（Fullなら完全版）reports/weekly/YYYYMMDD-WEEKLY.md を確かめ、
  `git add reports/weekly/YYYYMMDD-WEEKLY.md`（書き手が reports/flows/fuel_latest.yaml を更新した週はそれも）→ `git -c user.name=claude -c user.email=noreply@anthropic.com commit -m "report YYYYMMDD-WEEKLY"` → `git push origin main`。
  push が断られたら下の「push が断られたとき」に従う。
  reports/ 以外のファイルは変更しない。
  data ブランチには書かない。
  口座・保有・数量は本文に書かない。
- push が断られたとき：
  ・「fetch first」「non-fast-forward」と出た（ほかの更新が先に入っただけで、権限の問題ではない）→ `git pull -q --rebase origin main` のあと、もう一度 push する。
  ・それ以外（403 など、書き込みが許可されていない）→ このときだけ ToolSearch（query: "add_repo"）で名前が add_repo で終わるツールを探し、見つかれば
    add_repo（owner: "bakaho19920625-wq", repo: "market-data", access: "push"）を呼んでから、同じ push をもう1回だけ試す。
    それでも断られたら、エラー文をそのまま控え、配信の最後に「GitHub に保存できませんでした：（エラー文）」と1行で書く（推測で原因を書かない）。
    レポートの配信と保管ページへの保存は続ける。
- push が実際に断られたとき以外は、add_repo・gh・書き込みの道具の状態を、レポートにも配信にも書かない（何も送らず終了する回でも同じ）。
- 保管ページ（Artifact「米国株指標チェック」。前回の状態と直近180日の本文の置き場。F9の形式）への保存：
  1. `python3 /home/claude/market-data/tools/state_docs.py /home/claude/out/YYYYMMDD-WEEKLY.save.json /home/claude/market-data/reports/weekly/YYYYMMDD-WEEKLY.md --mode weekly_standard`（Full の週は `--mode weekly_full`）
     （書き手が作った save.json と本文から、reports/<report_id>・report_bodies/<report_id>・state/latest_weekly・state/scenarios の文書を /home/claude/out/ に作り、ArtifactData の batch に渡す writes を表示する。本文は変えない。どこにも送らない）。
  2. 表示された writes で ArtifactData の batch を呼ぶ（url は https://claude.ai/artifact/6NLifaXuDCqCTrWSoCojyq）。state/latest_weekly と state/scenarios には第3節で控えた version を if_version に付ける。
     同じ id の reports・report_bodies がすでにあるとき（訂正版）は、get で version を読んで if_version を付ける。
- 保管ページの本文の整理（180日）：ArtifactData の query で reports を読み（where [["as_of_market_et", "<", "<基準日の180日前 YYYY-MM-DD>"]]、limit 1000）、
  該当する各 id のうち body_pruned が真でないものについて report_bodies/<id> を get → delete（if_version はその version）し、reports/<id> を update で {body_pruned: true, body_archive: "reports/<daily|weekly>/<id>.md"} にする
  （reports/<id> の見出し等はそのまま残す。if_version を付ける。body_pruned が真のものは前週までに整理済みなので飛ばす）。
  削除件数を配信に1行添える。
  本文はGitHubの reports/ にあるので失われない。
- state/ledger は使わない（台帳はGitHubの ledger.json）。
  既存ドキュメントは読んだ version を if_version に指定する。
- 保存に失敗したら、その旨をユーザーに伝える。
- 読む用の保管ページ「米国株 週次レポート」への保存：GitHub への push のあとに、runbook/archive_page.txt の手順を種類 us_weekly で行う。

## 9. この実行での注意（無人で動くため）
- この実行には、途中で答える人がいない。道具を呼ばずに文だけを返すと、そこで実行が終わり、続きは誰も頼まない。
  第6節の配信と第7節の保存が終わるまで、次の作業の道具を呼び続ける。
- 次の4つの止まり方をしない：(1)「次は○○をします」と書いただけで終える、(2)「続けますか」と尋ねて待つ、
  (3) 決めなくても進められることを並べて判断を求める、(4) 区切り（書き手が書き終えた、点検が通った、push できた）で終える。
  途中経過を書くときは、次の道具の呼び出しと同じ返答の中に書く。
- 止まってよいのは、この手順書が「終了」と書いている場面だけ：仕様を読めない（第1節）、配信済み（第3節）、そして第6節の配信と第7節の保存がすべて終わったとき。
- 最初に、第1節〜第7節をやることリストに入れ（TaskCreate が使えるとき）、1つ終えるごとに消す。
- 障害（エラー、タイムアウト、空の結果、取得の失敗）は、原因を見て別の方法を試す。代わりの手順が決まっているものは、その節に書いてあるとおりにする。
- 保管ページへの書き込みが version の食い違いで断られたときは、get で version を読み直して、もう一度書く。
- GitHubのリポジトリのファイルは変更しない。
  例外は、データが古いときのワークフロー起動（weekly_runbook.txt 第2節）、レポート本文の reports/ への保存（同 第7節）、reports/flows/fuel_latest.yaml の更新（14項）だけ。
  data ブランチには書かない。口座・保有・売買ログは扱わない（未提供として扱う）。
- GitHub への書き込みは git の push だけで行う（第2節のデータ更新の起動と、第7節の保存）。
  add_repo と gh は、第7節の「push が断られたとき」以外では使わない。
  `gh auth status` も実行しない（gh が使えるときでも「The token in GH_TOKEN is invalid.」と出るので、判断材料にならない。2026-11-10 に確認）。
