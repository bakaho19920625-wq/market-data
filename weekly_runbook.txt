## 0. 原則
- 計算はGitHubの解析エンジン（analyze.py）が済ませている。Tapeチェックリスト、先導候補、セットアップ、ブレイク追跡、売りシグナル、
  セクター相対強度・調整耐性・RSライン、市場内部の拡張（breadth_ext）、先導セクターの推移（leadership）、ヘッジ条件（hedge）、
  長期SPY配分モデル（spy_model）は signals.json・ledger.json の値を使い、再計算しない
  （検証目的は可。食い違いは signals.json を優先して報告）。それ以外の時系列計算（週足Stage、SMA、HV等）はPythonで行う。
- マクロ、金融政策、金利、景気・雇用・物価、企業利益・EPS修正、評価、信用・ボラ、心理・フロー・FINRA、ドル・商品・地政学、
  セクター、季節性、次週のイベントはWeb検索で取得し、出典・基準日・単位・データ状態を付ける。
- 推測で埋めない。未確認の値は missing とし、D4のデータゲートを適用する。
- ユーザーの口座・保有は未提供として扱い、数量は出さない（チャットで示された範囲だけ使う）。
- 個別分析は半導体・テクノロジーの監視銘柄だけ。市場全体の先導候補はTape判定とセクター分布の表示にだけ使う。
- GitHubのリポジトリのファイルは変更しない。例外は、第2節のワークフロー起動と、第7節のレポート本文の reports/ への保存だけ。
- ［v1.1］書き方：状態を表す語は 05_Plain_Language_Glossary.txt（main。届かなければ保管ページの spec/plain_language.txt）の「言葉」で書き、
  数字と記号を括弧で後ろに付ける。記号は消さない。記号だけ・英語だけの行を作らない。表には「言葉」の列を置くか、数字の横に言葉を添える。
  Full の27項目・YAML の項目名は仕様どおり（YAMLは機械が読むので言葉に置き換えない）。本文の巻末に「読み方」（使った記号だけ、1行ずつ）。

## 2. データを取得する
1. data ブランチから manifest.json、signals.json、screen.csv、setups.csv、ledger.json、history_signals.csv、breadth.csv、prices_daily.csv.gz を取得する
   （https://raw.githubusercontent.com/bakaho19920625-wq/market-data/data/<ファイル名>。
   届かなければ git clone --depth 1 -b data https://github.com/bakaho19920625-wq/market-data.git）。
2. signals.as_of_market_date が直近の米国取引日（通常は金曜。NYSE休場日を除く）より古ければ、データ更新を自分で起動する：
   - mcp__claude-code-remote__add_repo（owner: "bakaho19920625-wq", repo: "market-data", access: "push"）でリポジトリを追加する
     （結果の指示どおりクローンしてよい）。
   - `gh workflow run update.yml --ref main -R bakaho19920625-wq/market-data`
   - `gh run list -R bakaho19920625-wq/market-data --workflow update.yml -L 1 --json databaseId,createdAt` でIDを取り、
     `gh run watch <ID> -R bakaho19920625-wq/market-data --exit-status --interval 20`（タイムアウト10分）で完了を待ってから取り直す。
   - それでも古ければ、基準日を明記してレポートを作り、冒頭で「GitHubのデータが最新ではありません」と警告する。
3. manifest.repo_last_commit_main から45日以上経過していれば、冒頭で「GitHubのリポジトリを更新してください
   （tickers.txt に1行コメントを足して保存）」と警告する。manifest.keepalive が failed でも同様。
4. 読込時はファイル名、基準日、行数、銘柄数、欠損・重複・分割疑義、出典種別を示す（CLAUDE.md 3節）。

## 4. モードを決める

  （判定条件が変わったため、前回のEと今回のCは同じ定義での変化ではない）。
- どちらにしたかと理由を、レポートの冒頭に書く。

## 5. レポートを作る
- 先頭は冒頭ブロック（05の0節の形）：
  - 「今日のひとこと」3〜4行：相場（Broad の点数と判定帯＋Tape レジームを05の1節の言葉で。例「土台は普通（Broad 52点）だが、値動きは高値圏で売りが増えている（C、確定）」）、
    半導体・テクノロジー（テック内部のラベルと SOXX の位置）、やること（05の5節。L/H を言葉で：例「買い持ちは控えめ（L2）、ヘッジは一部（H1）。新規は原則見送り」。
    ［v4.5］signals.hedge.allowed が真なら「ヘッジ：条件成立／未成立（損切り。置くかは判断）」を同じ行に）。
    ［v4.5］4行目に「長く持つ分の目安 ○%（buy／sell、○月○日から）」（signals.spy_model）。短期の「やること」と混ぜない。
  - 「なぜその判断か」3〜5行：Tape の判定理由（signals.tape.reasons）を言葉にしたものを最初に、押し上げた要因・抑えた要因を分けて、Broad と Tape の値から1行ずつ。
    一段強気・弱気にしなかった理由を1行。最後の1行は「判断が変わる条件」を数値で（upgrade／downgrade の条件）。
  - モードがFullの理由（第4節）は冒頭ブロックの直後に1行。
- report_id は YYYYMMDD-WEEKLY（YYYYMMDD は signals.as_of_market_date）。previous_id は前回の週次。
- 前回の週次と比較し、今週の日次レポートの判断変化を要約に含める。期日到来したシナリオを F6 で採点する（Brier）。
- Tape の表（C15.1）には、SPY/QQQ の配置、IX2、BR1〜BR3、LD1、index_state に加え、追補04の書き方どおり次を入れる：
  FB1（D+5維持率／平均リターン D+5・D+10／伸び判定 FB1_extends・FB1_stalling）、IX3（指数の崩れガード。成立なら理由：大型株主導の崩れ／指数の崩れ）、
  BR4（S&P500で高値から−20%以上の銘柄比率と4週前、ラベル）、C_support_met。市場内部とFB1は現在の構成銘柄からのproxy（生存者バイアス）と注記する。
- 半導体・テクノロジー節の冒頭に「テック内部」：signals.breadth_ext の tech（pct_down20 と4週前、pct_above_50sma、ラベル、XLKの位置）、
  ex_tech との差、megacap_led。stealth／broad_decline／megacap_led の書き方は追補04「レポートでの書き方」。
  ［v4.5］同じ行に監視グループ別の先導株数（signals.leadership.tech.by_group、今／4週前）。
- ［v4.5b］Tape表の直後に「4週間の推移」の小表（history_signals.csv の直近20営業日から、週ごとの最終日4行＋当日）：レジーム（確定）、大口の売り（IX2）、上向き銘柄の割合（BR1）、
  テック内部（BR5とラベル）、テック・半導体の先導株数、ヘッジ条件の成立日、長期モデルの合計点。値は転記し、再計算しない。
- ［v4.5］「先導セクターの推移」の小節（signals.leadership。Tape表の直後）：
  ・表：セクター別の先導株数（今／4週前／増減、多い順）と、セクターETFの市場比の強さ（3か月）の順位（今／4週前／変化）。
  ・新しく先導株になった銘柄の上位5と外れた銘柄の上位5（セクター、RS百分位、高値からの位置）。半導体・テクノロジーの先導株数（今／4週前。半分以下なら明記）。
  ・読み方を2行：どこに資金が向かっているか、半導体・テクノロジーは引っ張られているか置いていかれているか。
  ・B部（B4.8）の「セクター」項目のうち、先導株数とETFの市場比の強さ・順位はこの小節から引き、別に集計しない。B4.8の他の項目（1週の騰落、EPS修正、評価）はWebで補う。
- ［v4.5］「ヘッジ」（signals.hedge）：許可・今日の成立・解除の状態と、週内に成立した日（日次の key_events から）。目的（方向性かベータ低下か）と
  D部の上限（H1＝5〜15%、H2＝15〜30%）を添える。setup_level は条件がそろった場合の上限で、D部の最終 hedge_level とは別。置くかどうかは判断であり、エンジンは条件を出すだけ、と一言。
- ［v4.5］「長期SPY配分モデル」（signals.spy_model）：配分%、buy／sell、いつから、5項目の内訳、4週前の合計点、直近の変化。
  Tapeとの組み合わせの読み方を1行（例「長期は買い持ちのまま、短期は守り」）。長く持つ分（積立や段階売りの残し方）の参考であり、短期の売買判断には使わない。
  SPYの目安なので、SOXL等の3倍ETFに配分%をそのまま当てはめない、と一言添える。
- セクター相対強度・調整耐性・RSライン（追補03）は signals.sector_rs／correction_resilience／rs_lines から転記する。監視候補の順番であり買い判定ではない。
- Full は B10 の27項目すべてと D10 のフルYAML（UNIFIED_MARKET_STATE、checkpoint_version 4.1、specification_version 4.5、
  extensions.sector_leadership schema 1.3、extensions.breadth_ext BX-1.0、extensions.spy_model SM-1.0、extensions.hedge HG-1.0）。Standard は D9 の簡易YAML。
- 出力前に CLAUDE.md 8節の点検（構成、根拠、日付、基準日、計算ログ、Tapeチェックリスト、配分、確率合計100%、トリガー、本文とYAMLの一致）を行う。

## 7. 保存する
- ［v1.3］GitHubへの保存（全履歴の置き場。F9）：第2節で add_repo していなければ mcp__claude-code-remote__add_repo（owner: "bakaho19920625-wq", repo: "market-data", access: "push"）で追加し、
  結果の指示どおり /home/claude/market-data にクローン（あれば `git -C /home/claude/market-data pull -q --ff-only`）。本文（Fullなら完全版）を reports/weekly/YYYYMMDD-WEEKLY.md に書き、
  `git add reports/weekly/YYYYMMDD-WEEKLY.md` → `git -c user.name=claude -c user.email=noreply@anthropic.com commit -m "report YYYYMMDD-WEEKLY"` → `git push origin main`。
  push が拒否されたら配信にその旨を書く。reports/ 以外のファイルは変更しない。data ブランチには書かない。口座・保有・数量は本文に書かない。
- ArtifactData の batch で、F9の形式どおり reports/<report_id>（mode: "weekly_standard" または "weekly_full"）、
  report_bodies/<report_id>（200KB超なら要約にして truncated=true）、state/latest_weekly、state/scenarios を書く。
- ［v1.3］保管ページの本文の整理（180日）：ArtifactData の query で reports を読み（where [["as_of_market_et", "<", "<基準日の180日前 YYYY-MM-DD>"]]、limit 1000）、
  該当する各 id について report_bodies/<id> を get → delete（if_version はその version）し、reports/<id> を update で {body_pruned: true, body_archive: "reports/<daily|weekly>/<id>.md"} にする
  （reports/<id> の見出し等はそのまま残す。if_version を付ける）。削除件数を配信に1行添える。本文はGitHubの reports/ にあるので失われない。
- state/ledger は使わない（台帳はGitHubの ledger.json）。既存ドキュメントは読んだ version を if_version に指定する。
- 保存に失敗したら、その旨をユーザーに伝える。
