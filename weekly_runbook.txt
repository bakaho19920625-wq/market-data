## 2. データを取得する
0. ［v2.1］最初に作業用のコピーを用意する（データ更新の起動と reports/ への保存に使う。データが新しくても先に行う）：
   - `git clone https://github.com/bakaho19920625-wq/market-data /home/claude/market-data`（公開リポジトリなので事前の準備は要らない。すでにあれば `git -C /home/claude/market-data pull -q --ff-only`）。
   - GitHub への書き込みは git の push だけで行う（この節のデータ更新の起動と、第7節の保存）。add_repo と gh は、下の「push が断られたとき」以外では使わない。
     `gh auth status` も実行しない（gh が使えるときでも「The token in GH_TOKEN is invalid.」と出るので、判断材料にならない。2026-11-10 に確認）。
   - push が断られたとき：
     ・「fetch first」「non-fast-forward」と出た（ほかの更新が先に入っただけで、権限の問題ではない）→ `git pull -q --rebase origin main` のあと、もう一度 push する。
     ・それ以外（403 など、書き込みが許可されていない）→ このときだけ ToolSearch（query: "add_repo"）で名前が add_repo で終わるツールを探し、見つかれば
       add_repo（owner: "bakaho19920625-wq", repo: "market-data", access: "push"）を呼んでから、同じ push をもう1回だけ試す。
       それでも断られたら、エラー文をそのまま控え、配信の最後に「GitHub に保存できませんでした：（エラー文）」と1行で書く（推測で原因を書かない）。レポートの配信と保管ページへの保存は続ける。
   - push が実際に断られたとき以外は、add_repo・gh・書き込みの道具の状態を、レポートにも配信にも書かない（何も送らず終了する回でも同じ）。
1. data ブランチから manifest.json、signals.json、screen.csv、setups.csv、ledger.json、history_signals.csv、breadth.csv、prices_daily.csv.gz を取得する
   （https://raw.githubusercontent.com/bakaho19920625-wq/market-data/data/<ファイル名>。
   届かなければ git clone --depth 1 -b data https://github.com/bakaho19920625-wq/market-data.git）。
2. signals.as_of_market_date が直近の米国取引日（通常は金曜。NYSE休場日を除く）より古ければ、データ更新を自分で起動する：
   - ［v2.1］起動は git の push で行う（日次と同じ）。/home/claude/market-data（手順0）で
     `date -u +%Y-%m-%dT%H:%M:%SZ > refresh/request.txt && git add refresh/request.txt && git -c user.name=claude -c user.email=noreply@anthropic.com commit -m "refresh request" && git push origin main`。
     この push で .github/workflows/update.yml が動く（refresh/README.md）。push が断られたら手順0の「push が断られたとき」に従い、それでも駄目なときだけ
     `gh workflow run update.yml --ref main -R bakaho19920625-wq/market-data` を1回試す（エラーなら起動できなかったものとして先へ進む）。
   - 完了は git で確かめる：30秒おきに `git -C /home/claude/market-data fetch -q origin data && git -C /home/claude/market-data show FETCH_HEAD:manifest.json` の prices.as_of を見て、
     直近の取引日になるまで最大12分待ってから取り直す（raw.githubusercontent.com は数分古い値を返すことがあるので待ち合わせには使わない）。
   - それでも古ければ、基準日を明記してレポートを作り、冒頭で「GitHubのデータが最新ではありません」と警告する。
3. manifest.repo_last_commit_main から45日以上経過していれば、冒頭で「GitHubのリポジトリを更新してください
   （tickers.txt に1行コメントを足して保存）」と警告する。manifest.keepalive が failed でも同様。
4. 読込時はファイル名、基準日、行数、銘柄数、欠損・重複・分割疑義、出典種別を示す（CLAUDE.md 3節）。

## 5. レポートを作る
- 先頭は冒頭ブロック（05の0節の形）：
  - 「今日のひとこと」3〜4行：相場（Broad の点数と判定帯＋Tape レジームを05の1節の言葉で。例「土台は普通（Broad 52点）だが、値動きは高値圏で売りが増えている（C、確定）」）、
    半導体・テクノロジー（テック内部のラベルと SOXX の位置）、やること（05の5節。L/H を言葉で：例「買い持ちは控えめ（L2）、ヘッジは一部（H1）。新規は原則見送り」。
    ［v4.5］signals.hedge.allowed が真なら「ヘッジ：条件成立／未成立（損切り。置くかは判断）」を同じ行に）。
    ［v4.5］4行目に「長く持つ分の目安 ○%（buy／sell、○月○日から）」（signals.spy_model）。短期の「やること」と混ぜない。
  - 「なぜその判断か」3〜5行：Tape の判定理由（signals.tape.reasons）を言葉にしたものを最初に、押し上げた要因・抑えた要因を分けて、Broad と Tape の値から1行ずつ。
    一段強気・弱気にしなかった理由を1行。最後の1行は「判断が変わる条件」を数値で（upgrade／downgrade の条件）。
  - モードがFullの理由（第4節）は冒頭ブロックの直後に1行。
- report_id は YYYYMMDD-WEEKLY（YYYYMMDD は signals.as_of_market_date）。previous_id は前回の週次。
- 前回の週次と比較し、今週の日次レポートの判断変化を要約に含める。期日到来したシナリオを F6 で採点する（Brier）。

  BR4（S&P500で高値から−20%以上の銘柄比率と4週前、ラベル）、C_support_met。市場内部とFB1は現在の構成銘柄からのproxy（生存者バイアス）と注記する。

  ［v4.5］同じ行に監視グループ別の先導株数（signals.leadership.tech.by_group、今／4週前）。
- ［v4.5b］Tape表の直後に「4週間の推移」の小表（history_signals.csv の直近20営業日から、週ごとの最終日4行＋当日）：レジーム（確定）、大口の売り（IX2）、上向き銘柄の割合（BR1）、
  テック内部（BR5とラベル）、テック・半導体の先導株数、ヘッジ条件の成立日、長期モデルの合計点。値は転記し、再計算しない。
- ［v4.5］「先導セクターの推移」の小節（signals.leadership。「4週間の推移」の次）：
  ・表：セクター別の先導株数（今／4週前／増減、多い順）と、セクターETFの市場比の強さ（3か月）の順位（今／4週前／変化）。
  ・新しく先導株になった銘柄の上位5と外れた銘柄の上位5（セクター、RS百分位、高値からの位置）。半導体・テクノロジーの先導株数（今／4週前。半分以下なら明記）。
  ・読み方を2行：どこに資金が向かっているか、半導体・テクノロジーは引っ張られているか置いていかれているか。
  ・B部（B4.8）の「セクター」項目のうち、先導株数とETFの市場比の強さ・順位はこの小節から引き、別に集計しない。B4.8の他の項目（1週の騰落、EPS修正、評価）はWebで補う。

- ［v4.5］「長期SPY配分モデル」（signals.spy_model）：配分%、buy／sell、いつから、5項目の内訳、4週前の合計点、直近の変化。
  Tapeとの組み合わせの読み方を1行（例「長期は買い持ちのまま、短期は守り」）。長く持つ分（積立や段階売りの残し方）の参考であり、短期の売買判断には使わない。

## 6. 配信する
- ［v2.2］SendUserMessage の冒頭サマリは**1画面**（日本語でおよそ800〜1,200字）。全文は添付の本文で読めるので、配信には判断に要るものだけを書く：
  1. 冒頭ブロック（第5節と同じ文：今日のひとこと3〜4行＋なぜその判断か。ヘッジと長く持つ分の目安はここに入っている）
  2. 前回から変わった点：Tape・Broad の変化（定義変更があればその旨）、持っている分の上限とヘッジの上限（L/H）が変わったか、先導セクターの入れ替わり、半導体・テクノロジーの先導株数（4週前比）。モードが Full ならその理由を1行
  3. 1行ずつ：買い戻しの燃料計（棒の行と読み方。追補08）／強気の材料・弱気の材料を各2点まで
  4. 来週のイベント（日付つきで3〜5件）と、データ状態で伝えるべきこと（未更新・missing の多い分野・補完。なければ書かない）
  土台と値動きの一致（Alignment）の説明、27項目の中身、ステージの表は配信に書かない（本文にある）。最後に「全文は添付のファイル」と1行。すべて05の言葉で、記号は括弧。
- 本文全体を「YYYYMMDD-WEEKLY.md」として書き、SendUserFile で送る。1回に収まらなければ分割し、途中までのものを完成版と表示しない。

## 7. 保存する
- ［v1.3］GitHubへの保存（全履歴の置き場。F9）：第2節の手順0で用意した /home/claude/market-data で `git pull -q --ff-only`（無ければ手順0のとおりクローン）。本文（Fullなら完全版）を reports/weekly/YYYYMMDD-WEEKLY.md に書き、

## 8. 欠けた週の補完（v2.0。日曜の定期実行が利用上限などで動かなかった週の週次を後日作る）
- きっかけ：日次の冒頭の警告（先週の週次が未作成）か、ユーザーの「週次を補完して」。自動では作らない（週次は重い）。
- 基準日：欠けた週の金曜（休場なら最後の取引日）。それ以降の取引日の足が data ブランチに入っているので、日次の第8節と同じ補完実行で当日の値を作る：
  `python3 analyze.py --out /home/claude/bf_D --tickers tickers.txt --as-of D --replay-ledger 130 --prev-history /home/claude/bf_D/history_signals.csv`
  （/home/claude/bf_D は data ブランチのコピー。signals.json・screen.csv・setups.csv が D 時点の値になる。history_signals.csv の D の行と Tape の値が一致することを確かめる）。
- マクロ（第5節のB部）は、その週末時点の値を調べて使う（発表日が基準日より後の統計は使わない。取れない値は missing／period_mismatch）。
- モードは第4節のとおり（欠けた週が月初や定義変更後なら Full）。タイトルに「（補完版）」、冒頭に「この週の週次は配信できなかったため、後日 D 時点のデータで作り直したもの。
  判定・ステージ・候補はエンジンの再計算で当時と同じ。ニュースとマクロは作成時点で調べ直したもの」と書く。
- シナリオ（F6）は基準日 D の終値で立て、期日は D の21営業日後。採点対象の過去シナリオがあれば通常どおり採点する。

  state/scenarios には補完した週のシナリオも追加する（期日順に並べる）。
