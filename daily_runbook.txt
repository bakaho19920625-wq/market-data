## 2. データの新しさ
- 直近の米国取引日（土日・NYSE休場日を除く、日本時間の今日の前日にあたるET日付）を求める。
- 前日が休場日 → 7:07 の1回目は「新しい取引日はありません（休場）」と短く送って終了（保存しない）。
  9:07・12:07 の再試行では何も送らずに終了する。
- signals.as_of_market_date がその取引日より古い（GitHubの予約実行は数時間遅れることがある）：
  ・まず自分でデータ更新を起動して待つ（GitHub の予約実行は数時間遅れたり来なかったりするので、これが主な経路）。
   起動は git の push で行う：
    /home/claude/market-data（第1節）で
    `date -u +%Y-%m-%dT%H:%M:%SZ > refresh/request.txt && git add refresh/request.txt && git -c user.name=claude -c user.email=noreply@anthropic.com commit -m "refresh request" && git push origin main`。
    この push で .github/workflows/update.yml が動く（refresh/README.md）。
    push が断られたら第9節の「push が断られたとき」に従い、それでも駄目なときだけ
    `gh workflow run update.yml --ref main -R bakaho19920625-wq/market-data` を1回試す（エラーなら起動できなかったものとして先へ進む）。
    完了は git で確かめる：30秒おきに `git -C /home/claude/market-data fetch -q origin data && git -C /home/claude/market-data show FETCH_HEAD:manifest.json` の prices.as_of を見て、
    直近の取引日になるまで最大12分待つ（raw.githubusercontent.com は数分古い値を返すことがあるので待ち合わせには使わない）。
    （ワークフローは前営業日の足が入るまで10分おきに最大6回取り直すので、Yahooが未確定なら12分では終わらない。その場合は次へ）
  ・それでも古く、日本時間9時より前の実行（7:07の1回目）→ ユーザーには何も送らず終了（保存しない）。
   9:07の再試行に任せる。
  ・それでも古く、日本時間9時以降の実行（9:07・12:07の再試行）→ 「GitHubのデータが更新されていません（基準日○○、生成○○）」と送って終了（保存しない。12:07 は 9:07 が利用上限で動けなかった日のためのもので、同じ文が2回届くことがある）。
    manifest.prices.yahoo_incomplete に基準日より新しい日付があれば、原因として「Yahooが○○日の終値を未確定（空欄）のまま配信しているため。修正されしだい自動で取り込みます」と添える。

## 3. 配信済みの確認
- 同じ基準日の日次がすでに保存済み（state/latest_daily の as_of_market_et が一致、または reports/daily/YYYYMMDD-DAILY.md がある）なら、1回目でも再試行でも何も送らず終了する。
  12:07 の再試行は、7:07・9:07 が利用上限などで動けなかった日のためのもの。
  すでに配信済みならこの規則で静かに終わる。
  この回は SendUserMessage を使わない（通知を出さない）。
  runbook/archive_page.txt の手順 1〜3（種類 us_daily）だけを行い（ページに入っていない日次があれば入れる）、
  最後の返答を次の1行だけにする：「YYYY-MM-DD（基準日）の日次レポートは配信済みです。レポートはここに並んでいます：https://claude.ai/artifact/DLehq35r7icxPU4odqs13R」
  配信済みなら、ここで終わる。第4節から先と runbook/daily_write.txt は読まなくてよい。

## 4. 欠けた日の確認
- 欠けた日の確認：reports/daily/ に無い直近の取引日があれば、今日の日次の前に runbook/daily_backfill.txt を読んで補完版を作る（最大3日分）。

## 5. リポジトリの活動と、前回の状態
- リポジトリの活動（60日停止の予防）：manifest.repo_last_commit_main から経過日数を出す。
  45日以上なら、レポート冒頭に「GitHubのリポジトリを更新してください（tickers.txt を開いて1行コメントを足して保存するだけで足ります）」と警告する。
  manifest.keepalive が "failed" なら、その旨も添える。
  該当したら、第6節で書き手に伝える（レポートの冒頭に書かせる）。
- 前回の状態：保管ページ（Artifact「米国株指標チェック」https://claude.ai/artifact/6NLifaXuDCqCTrWSoCojyq）のデータベースから、ArtifactData の get で state/latest_daily と state/scenarios を読む（collection: "state"）。
  out_dir: "/home/claude/state" を付けて、ファイルに保存する（書き手が読む）。state/latest_daily の version を控える（第9節の保存で使う）。
  同じ基準日の日次が保存済みなら二重保存しない。

## 7. 点検
- 自分でも点検プログラムを実行する（書き手の報告だけで済ませない。数秒で終わる）：
  `python3 /home/claude/market-data/tools/check_report.py us_daily /home/claude/market-data/reports/daily/YYYYMMDD-DAILY.md --data /home/claude/mkt`
- 「不合格」の行があれば、同じ書き手に戻して直させる（SendMessage。最大2回）。
  戻すときは、不合格の行をそのまま貼り、「次の項目がまだ残っています。直してから、もう一度点検の結果を返してください」と、残っている項目を名指しする。
  SendMessage が使えないとき、または書き手が応えないときは、不合格の節だけ自分で直す（その節のファイルを読んでから）。
- 2回直しても残った不合格は、配信の4（データ状態で伝えるべきこと）に「点検で残った項目：○○」と1行で書く。配信は止めない。
- 点検プログラムそのものが動かない・途中で止まるときは、点検を飛ばして先へ進み、配信の同じ場所に「点検プログラムが動かなかった」と1行で書く。
- 「注意」の行は不合格ではない。読んで、直す必要があるものだけ直させる。

## 8. 配信
- SendUserMessage は**1画面**（日本語でおよそ600〜900字。重要な変化が多い日でも1,200字まで）。
  全文は添付の本文で読めるので、配信には判断に要るものだけを書く：
  1. 冒頭ブロック（レポートの冒頭と同じ文：今日のひとこと3〜4行＋なぜその判断か。ヘッジと長く持つ分の目安は「やること」の行と4行目に入っている）
  2. 重要ポイント（レポートの1節。前日から変わったこと。なければ「本日の重要イベントなし」）
  3. 1行ずつ：Daily Plan の候補数（候補があれば銘柄とピボット）／買い戻しの燃料（Broad の節の1行）
  4. 今夜〜明日のイベント（当日と翌営業日のものだけ）と、データ状態で伝えるべきこと（未更新・取得失敗・補完・週次未作成。なければ書かない）
  Tape の表、先導セクター、テック内部の内訳、ステージ、RSライン、セットアップの一覧は配信に書かない（本文にある。その日に変わったものは 2 に入っている）。
  最後に「全文は添付のファイルと、保管ページ（これまでの日次が並ぶ）：https://claude.ai/artifact/DLehq35r7icxPU4odqs13R」と1行（このリンクは毎回出す）。
  すべて05の言葉で、記号は括弧。
- 本文全体を YYYYMMDD-DAILY.md に書き、SendUserFile で送る。
- 送る前に、配信の文を /home/claude/delivery.txt に書き、`python3 /home/claude/market-data/tools/check_report.py delivery /home/claude/delivery.txt --max 1200 --link https://claude.ai/artifact/DLehq35r7icxPU4odqs13R` で長さと最後の行を確かめる。

## 9. 保存
- report_id：YYYYMMDD-DAILY（基準日）。
- GitHubへの保存（全履歴の置き場。F9）：第1節で用意した /home/claude/market-data で `git pull -q --ff-only`。
  書き手が書いた reports/daily/YYYYMMDD-DAILY.md を確かめ（同じIDは上書き）、`git add reports/daily/YYYYMMDD-DAILY.md`（書き手が reports/flows/fuel_latest.yaml を更新した日はそれも）→
  `git -c user.name=claude -c user.email=noreply@anthropic.com commit -m "report YYYYMMDD-DAILY"` → `git push origin main`。
  push が断られたら下の「push が断られたとき」に従う。
  reports/ 以外のファイルは変更しない。
  data ブランチには書かない。
  公開リポジトリなので口座・保有・数量は本文に書かない（原則どおり）。
- push が断られたとき：
  ・「fetch first」「non-fast-forward」と出た（ほかの更新が先に入っただけで、権限の問題ではない）→ `git pull -q --rebase origin main` のあと、もう一度 push する。
  ・それ以外（403 など、書き込みが許可されていない）→ このときだけ ToolSearch（query: "add_repo"）で名前が add_repo で終わるツールを探し、見つかれば
    add_repo（owner: "bakaho19920625-wq", repo: "market-data", access: "push"）を呼んでから、同じ push をもう1回だけ試す。
    それでも断られたら、エラー文をそのまま控え、配信の最後に「GitHub に保存できませんでした：（エラー文）」と1行で書く（推測で原因を書かない）。
    レポートの配信と保管ページへの保存は続ける。
- push が実際に断られたとき以外は、add_repo・gh・書き込みの道具の状態を、レポートにも配信にも書かない（何も送らず終了する回でも同じ）。
- 保管ページ（Artifact「米国株指標チェック」。前回の状態と直近180日の本文の置き場。F9の形式）への保存：
  1. `python3 /home/claude/market-data/tools/state_docs.py /home/claude/out/YYYYMMDD-DAILY.save.json /home/claude/market-data/reports/daily/YYYYMMDD-DAILY.md --mode daily`
     （書き手が作った save.json と本文から、reports/<id>・report_bodies/<id>・state/latest_daily の3つの文書を /home/claude/out/ に作り、ArtifactData の batch に渡す writes を表示する。本文は変えない。どこにも送らない）。
  2. 表示された writes で ArtifactData の batch を呼ぶ（url は https://claude.ai/artifact/6NLifaXuDCqCTrWSoCojyq）。state/latest_daily には第5節で控えた version を if_version に付ける。
     同じ id の reports・report_bodies がすでにあるとき（訂正版）は、get で version を読んで if_version を付ける。
  保管ページは直近180日の置き場（整理は週次が行う）。
  state/ledger は使わない（台帳はGitHubの ledger.json が正本）。
  state/scenarios は週次が更新する。
  失敗したらユーザーに伝える。
- 読む用の保管ページ「米国株 日次レポート」への保存：GitHub への push のあとに、runbook/archive_page.txt の手順を種類 us_daily で行う。

## 10. この実行での注意（無人で動くため）
- この実行には、途中で答える人がいない。道具を呼ばずに文だけを返すと、そこで実行が終わり、続きは誰も頼まない。
  第8節の配信と第9節の保存が終わるまで、次の作業の道具を呼び続ける。
- 次の4つの止まり方をしない：(1)「次は○○をします」と書いただけで終える、(2)「続けますか」と尋ねて待つ、
  (3) 決めなくても進められることを並べて判断を求める、(4) 区切り（書き手が書き終えた、点検が通った、push できた）で終える。
  途中経過を書くときは、次の道具の呼び出しと同じ返答の中に書く。
- 止まってよいのは、この手順書が「終了」と書いている場面だけ：休場とGitHubデータ未更新（第2節）、配信済み（第3節）、そして第8節の配信と第9節の保存がすべて終わったとき。
- 最初に、第1節〜第9節をやることリストに入れ（TaskCreate が使えるとき）、1つ終えるごとに消す。
- 障害（エラー、タイムアウト、空の結果、取得の失敗）は、原因を見て別の方法を試す。代わりの手順が決まっているものは、その節に書いてあるとおりにする。
- 保管ページへの書き込みが version の食い違いで断られたときは、get で version を読み直して、もう一度書く。
- GitHubのリポジトリのファイルは変更しない。
  例外は、データが古いときのワークフロー起動（daily_runbook.txt 第2節）、レポート本文の reports/ への保存（同 第9節）、週の最初の日次での reports/flows/fuel_latest.yaml の更新（Broad の節）だけ。
  data ブランチには書かない。口座・保有・売買ログは扱わない（未提供として扱う）。
- GitHub への書き込みは git の push だけで行う（第2節のデータ更新の起動と、第9節の保存）。
  add_repo と gh は、第9節の「push が断られたとき」以外では使わない。
  `gh auth status` も実行しない（gh が使えるときでも「The token in GH_TOKEN is invalid.」と出るので、判断材料にならない。2026-11-10 に確認）。
